# Power Code App Playbook

## 1. Purpose

This file is a generic reference for building a **Power Apps Code App** with a modern TypeScript frontend and Dataverse integration.

Use this when starting a new Code App project so an AI agent or developer understands:

- how the app is structured
- how it connects to the Power Apps environment
- how code is pushed to the hosted Power App
- how Dataverse tables are added as Code App data sources
- how to retrieve and create records correctly
- how to handle lookup, choice, currency, and text fields

This guide is intentionally generic and reusable across future Code App applications.

---

## 2. What A Power Apps Code App Is

A Power Apps Code App is a frontend application that runs inside the Power Apps environment but is built using code.

Typical stack:

- React + TypeScript
- Vite or similar frontend tooling
- Power Apps Code App runtime
- Dataverse as backend data source

The app is pushed into Power Apps and runs there using the authenticated runtime provided by the environment.

That means:

- no custom browser auth flow is required for Dataverse calls
- Dataverse access should go through the Power Apps runtime client
- tables must be added as Code App data sources, not only exist in Dataverse

---

## 3. Recommended App Architecture

Use a layered structure so UI and Dataverse logic stay separated.

Recommended layers:

- `src/components`
  UI and reusable visual components
- `src/pages`
  page-level screens
- `src/domain`
  domain models and app-facing types
- `src/api`
  API contracts and adapter implementations
- `src/api/dataverse`
  Dataverse adapter files
- `src/services`
  orchestration and business logic
- `src/hooks`
  reusable state and data hooks
- `src/mocks`
  mock implementations for local or staged development
- `src/generated`
  Power Apps generated Dataverse services and models

Recommended rule:

- UI should not directly contain Dataverse-specific mapping logic
- generated files should never be edited manually
- any Dataverse normalization/mapping should happen in adapter or service files

---

## 4. How We Build A Code App

Typical flow:

1. create the frontend app
2. configure Power Apps Code App support
3. build UI components and pages
4. add Dataverse tables as data sources
5. use generated services for create/retrieve/update/delete
6. build locally
7. push to Power Apps

Core local commands usually include:

- `npm install`
- `npm run dev`
- `npm run build`
- `npx tsc -b`
- `npx power-apps run`
- `npx power-apps push`

---

## 5. How The App Connects To Power Apps

The Power Apps Code App project is connected through project configuration files generated by the Power Apps CLI/runtime.

Important files:

- `power.config.json`
- `.power/schemas/appschemas/dataSourcesInfo.ts`
- `.power/schemas/dataverse/*.Schema.json`

These files tell the app:

- which environment resources it knows about
- which Dataverse tables are registered as app data sources
- what generated services/models should exist

Power Apps generated services use:

- `@microsoft/power-apps/data`
- `getClient(dataSourcesInfo)`

This is the preferred integration pattern.

---

## 6. How To Connect A New Code App To A Power Apps Environment

At a high level:

1. create or open the Code App project
2. make sure the Power Apps CLI is authenticated
3. connect the project to the target environment/app
4. add required Dataverse data sources
5. build and push

Important concept:

- the Power Apps maker portal URL is **not** the same thing as the Dataverse org URL

Examples:

- Maker portal URL:
  - `https://make.powerapps.com/...`
- Dataverse org URL:
  - `https://yourorg.crm.dynamics.com`
  - `https://yourorg.crm15.dynamics.com`

When adding Dataverse data sources, use the **Dataverse org URL**.

## 7. How To Add Dataverse Tables To A Code App

This is one of the most important rules.

A table can exist in:

- the Dataverse environment
- a solution inside that environment

But that is still **not enough** for a Code App.

The table must also be added to the **Code App project as a data source**.

If not, the app will not get:

- generated schema metadata
- generated TypeScript models
- generated TypeScript services
- runtime datasource wiring

### Generic command

```bash
npx power-apps add-data-source --api-id dataverse --resource-name <logical-table-name> --org-url "https://<org>.crm.dynamics.com"
```

### Example

```bash
npx power-apps add-data-source --api-id dataverse --resource-name dga_classification --org-url "https://dge.crm15.dynamics.com"
```

### After adding a table, verify these outputs

- `power.config.json`
- `.power/schemas/appschemas/dataSourcesInfo.ts`
- `.power/schemas/dataverse/*.Schema.json`
- `src/generated/models/*`
- `src/generated/services/*`

## 8. Generated Services Pattern

After a table is added, Power Apps generates a service and model.

Typical generated methods:

- `.create(record)`
- `.update(id, changedFields)`
- `.delete(id)`
- `.get(id, options)`
- `.getAll(options)`
- `.getMetadata(options)`

Under the hood these call:

- `createRecordAsync`
- `updateRecordAsync`
- `deleteRecordAsync`
- `retrieveRecordAsync`
- `retrieveMultipleRecordsAsync`
- `executeAsync`

Generic example:

```ts
import { AccountsService } from '@/generated/services/AccountsService'

const result = await AccountsService.getAll({
  select: ['name', 'accountid'],
  orderBy: ['name asc'],
})
```

---

## 9. Recommended Dataverse Usage Pattern

Do not let pages directly depend on generated models everywhere.

Preferred pattern:

1. generated service retrieves raw Dataverse rows
2. adapter/service maps them into clean app domain types
3. UI uses domain types only

Example layering:

- generated service:
  - `Dga_classificationsService.getAll(...)`
- adapter:
  - `src/api/dataverse/dataverseClassificationsApi.ts`
- service:
  - `src/services/classificationService.ts`
- hook:
  - `src/hooks/useClassificationPicker.ts`
- UI:
  - modal/page/component

This keeps the app easier to maintain and easier to switch between mock and Dataverse-backed data.

## 10. How To Retrieve Records

Preferred pattern:

```ts
GeneratedService.getAll({
  select: [...],
  filter: '...',
  orderBy: ['... asc'],
})
```

### Generic example

```ts
const result = await SomeTableService.getAll({
  select: ['field1', 'field2', '_lookupfield_value'],
  filter: `_parent_value eq ${recordId}`,
  orderBy: ['field1 asc'],
})
```

### Good practice

- select only the fields needed
- filter using lookup raw values where needed
- sort in the query when possible
- normalize the generated model into domain types after retrieval

---

## 11. How To Create Records

Use the generated service `.create(...)`.

### Generic example

```ts
await SomeTableService.create({
  field_text: 'Example',
  'lookupfield@odata.bind': `/target_tables(${targetId})`,
} as Omit<SomeTableBase, 'primaryid'>)
```

### Important note

Generated TypeScript models can sometimes mark fields as required even when Dataverse will populate them at runtime.

So:

- do not edit generated files
- build payloads in a wrapper service
- cast in the wrapper if needed

This keeps generated code untouched and the workaround localized.

## 12. Field Handling Rules

These rules are important for consistent Dataverse behavior.

### Choice / Option Set

On retrieve:

- use formatted label for display when available
- keep raw numeric value if needed for app logic

On create/update:

- use the raw numeric option value

Example:

```json
"dga_classification_level@OData.Community.Display.V1.FormattedValue": "L1",
"dga_classification_level": 1
```

### Lookup

On retrieve:

- use formatted lookup value for display
- preserve raw lookup id for logic, filtering, and associations

Example:

```json
"_dga_parent_classification_value@OData.Community.Display.V1.FormattedValue": "Data Management - L1005",
"_dga_parent_classification_value": "1a30dd6b-5b49-f111-bec7-70a8a521c043"
```

On create/update:

- use `@odata.bind`

Example:

```ts
'dga_classification@odata.bind': `/dga_classifications(${classificationId})`
```

### Currency

On retrieve:

- treat as numeric

On create/update:

- send numeric value
- in this project we treat it as integer-style numeric unless table rules require something more specific

### Text / Multiline Text

On retrieve:

- use plain string field

On create/update:

- send plain string field

## 13. Common Dataverse Mapping Strategy

When mapping a Dataverse row into UI data, preserve both:

- display-friendly values
- raw system values when the app still needs them

Typical examples:

- raw choice value + formatted choice label
- raw lookup id + formatted lookup label
- raw text fields as-is
- numeric currency values as numbers

This is especially important when:

- rendering a label in UI
- later updating the same record
- filtering child records by parent lookup
- rebuilding classification hierarchies from lookup ids

---

## 14. Example: Hierarchy / Self-Relationship Table

If a Dataverse table references itself, such as a classification hierarchy:

- retrieve all relevant rows
- store each row in a map by id
- rebuild parent/child relationships in app code
- compute paths such as `L1 / L2 / L3 / GL`

Useful pattern:

- raw table gives parent lookup id
- app reconstructs tree
- UI consumes a hierarchy-ready structure

This is often cleaner than trying to hardcode levels in the UI.

## 15. Mock Data And Dataverse Data

When starting a new Code App, it is common to begin with mock data.

Recommended pattern:

- define a shared API contract
- implement a mock adapter
- implement a Dataverse adapter
- switch source through config/provider layer

Example:

- `src/api/projectsApi.ts`
- `src/mocks/mockProjectsApi.ts`
- `src/api/dataverse/dataverseProjectsApi.ts`
- `src/services/projectsApiProvider.ts`

This makes it easy to:

- prototype UI quickly
- gradually replace mock logic with Dataverse
- keep pages stable while backend implementation changes

## 17. How To Push Code To Power Apps

After local build passes:

```bash
npx power-apps push
```

What this does:

- packages the current frontend build
- uploads it to the connected Power Apps Code App
- makes the latest version available in the hosted app runtime

After push, Power Apps returns a play URL for testing.

## 18. Generic Checklist For New Code Apps

When starting a fresh app, follow this checklist.

### Project setup

1. create the app structure
2. keep UI, services, adapters, and domain types separated
3. keep generated code untouched

### Power Apps setup

1. connect the project to the target environment
2. confirm `power.config.json` exists
3. confirm `.power/schemas/...` exists

### Dataverse setup

1. identify required tables
2. get the Dataverse org URL
3. add each table using `add-data-source`
4. verify generated services/models

### Implementation

1. create adapter wrappers around generated services
2. normalize Dataverse models into domain types
3. use service/hook layers in UI
4. preserve raw ids and formatted labels where needed

### Validation

1. run `npx tsc -b`
2. run `npm run build`
3. push with `npx power-apps push`
4. test in hosted Power Apps runtime

---

## 19. Practical Rules For Future AI Agents

If an AI is using this guide for a new Code App project, it should follow these rules:

- do not manually edit generated `src/generated/*` files
- do not assume a Dataverse table is ready just because it exists in the environment
- always verify that the table was added as a Code App data source
- use generated services for Dataverse calls
- keep business logic in service or adapter layers
- preserve lookup ids and choice raw values during normalization
- use formatted labels only for display
- build before pushing
- treat hosted Power Apps runtime as the final source of truth for Dataverse-connected behavior

---

## 20. Summary

The generic Code App pattern is:

1. build frontend in TypeScript
2. connect it to Power Apps
3. add Dataverse tables as Code App data sources
4. use generated Power Apps services for CRUD
5. map Dataverse records into clean app domain models
6. build locally
7. push to Power Apps
8. validate in hosted runtime

If this structure is followed, future Code Apps can be built faster, integrated with Dataverse more safely, and maintained more easily.
